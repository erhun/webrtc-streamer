# 升档阶段的码率控制

本次修复针对 `BitrateLadder` 的跨级升档和 `SurfaceEncoder` 的码率突变。
例如，最低档连续收到 5 秒的 2.3 Mbps 反馈后，单次 14 Mbps 反馈不再允许直接升到 12 Mbps 档。

## 行为

- 每次只升一级，下一次升级需要重新满足完整的 5 秒稳定窗口。
- 严重降档后的恢复也使用完整窗口，移除原有 2 秒快速升档通道。
- 低于下一档升级阈值、零预算、peer reset 或超过 2 秒的反馈间隔会取消升档候选。
  `maxFeedbackGapMs` 可以配置，但应结合实际 `SetRates` 回调频率验证；长期缺少反馈时保持档位，不凭空假定带宽稳定。
- 在反馈回调入口更新梯子，避免编码线程合并反馈或原来的 100 ms 节流漏掉短暂低预算。
  编码线程在同一把锁下读取预算和档位快照；MediaCodec 操作仍全部留在编码线程。
- 新增 `BitrateRamp`：上升速率为每秒 25%，低码率时至少允许每秒增加 100 kbps，但始终不超过当前预算和档位目标。
  单次更新最多使用 1 秒增长额度；暂停不累计额度。下降立即应用，不受升档计时或上升斜坡限制。
- 分辨率切换时也使用渐增后的编码目标，避免一边重启编码器、一边直接切到新档位的满码率。
- 保留普通降档的 3 秒防抖、严重降档的 1 秒冷却以及跨级降档能力。

默认策略偏向保持低延迟，画质恢复会比原来的跨级升档慢。斜坡约束的是 MediaCodec 的目标码率，
不是实际编码输出或 RTP 线速的硬上限；CBR 编码器仍可能输出较大的 IDR。
这些参数需要在目标设备和弱网条件下测量后调整。

## 验证

```sh
python3 tests/run_video_adaptation.py
```

需要带 `jdk.compiler` 模块的 JDK 17 或更新版本，可通过 `JAVA` 环境变量选择 Java 可执行文件。
脚本使用项目真实 Java 类，开启 `-Xlint:all -Werror`，覆盖跨级尖峰、逐级稳定窗口、严重降档恢复、
短暂低预算、暂停、反馈中断、peer reset、降档防抖、码率斜坡及立即降码率，并解析全部服务端 Java 源码。
解析只检查语法，不代替 Android 类型检查。
该脚本也已接入 `tests/run_regressions.py`；旧的梯子测试已迁移到独立的 `VideoAdaptationTest`。

构建环境具备 Android SDK 和 Gradle 依赖时，还应执行：

```sh
./gradlew -p server test checkstyle lint
./gradlew -p server assembleDebug
```

本次仅修改 Java 控制逻辑，未修改 JNI，也未重新生成 APK 或 native 库。
当前执行环境无法下载 Gradle，Android 测试、Checkstyle、lint 和 APK 构建尚未验证。
完整的轻量回归入口在本次新增测试通过后，仍被既有的 `NativeEncoderBridge` / `Ln` 编译依赖缺失阻塞；
本次未修改该独立问题，不能把定向测试通过视作全量回归通过。

## 真机验收与剩余范围

在相同网络条件下对比固定低档、固定高档和动态升档，记录升级前后至少 5 秒的预算、档位、
实际编码码率、实际 fps、IDR 大小及数量、pacer 最老包等待时间、RTT、丢包增量和卡顿时长。
重点检查：尖峰反馈不再跨级；每次升级重新等待稳定窗口；目标码率逐步增加；预算下降立即生效。
同时确认实际反馈间隔满足新鲜度要求，避免稳定网络下长期无法升级。

关键帧请求合并、真实采集帧率控制、pacer 队列参与升档决策仍需独立实现和真机验证。
此次修复不宣称已消除所有切档丢包，也不改变 FEC、NACK 或额外添加发送缓存。
