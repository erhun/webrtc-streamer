# 低码率、低帧率与质量波动排查

## 当前报告能说明什么

报告：264×480、解码/呈现约 10fps，JNI 输入和 WebRTC 输出均约 9.5fps，分配/配置 35kbps，编码输出 43kbps，
RTT 34ms，单次接收丢包率 10%，发送等待 5.4ms，接收驻留 70.9ms，目标/最低缓冲约 419ms。

- 480 长边、10fps 对应当前最低自适应档。帧率在 JNI 输入之前已经很低；该快照没有显示明显的浏览器解码瓶颈。
  `max_fps=60` 只是上限，不能覆盖弱网档位，也不能让静止画面产生真实的新帧。
- `分配码率` 原来仅展示 `SetRates.bitrate`，它是编码器修正后的目标，不能直接称为线路带宽或原始 BWE。
  仅凭它无法断言是物理网络、拥塞窗口、视频分配还是编码器超调修正导致限速。
- 34ms RTT 不能排除丢包；一秒低包量下的 10% 也不足以证明持续 10% 链路丢包。
- 采集帧龄包含编码到 JNI 入口的时间，不是输入到显示的端到端延迟。
  419ms 缓冲目标也不是已测得的端到端延迟，不能与 70.9ms 驻留直接相加。
- 43kbps 高于 35kbps 目标可能受关键帧、参数集、硬件码控及采样窗口影响；需要连续观测，不能据此直接认定码控失效。

## 本次修复

1. 保留反馈中的码率余量用于升档判断，只允许选择配置上限能支持的档位，实际编码目标仍受上限约束。
   原实现先把观察值截断到上限，例如 2Mbps，然后要求超过 2Mbps×1.12 才升入 960/30 档，因此永远无法进入该档。
   新回归验证高带宽下能够达到 2Mbps 配置对应的最高档，同时真实 35kbps 仍降至生存档，不强行提速。
2. 质量显示改为近五秒按包数加权的丢包率，保留迟到包引起的负丢包修正，至少二十包才评级；
   变化需要持续确认，降级两秒、恢复四秒。显示用于观察，不参与服务器码率控制。
3. 缓冲诊断同时检查实测驻留与目标/最低缓冲。目标约 419ms 时提示目标偏高，不再仅因驻留较低就给出笼统的低延迟提示。
4. 补充原始视频目标、视频带宽分配、反馈龄、当前选中发送路径的带宽估计，避免混淆反馈层级。
5. 诊断共享控制通道，原先每秒发送完整 outbound JSON 也会占用低带宽。
   现只发送视频必要计数及当前选中路径，单条应用负载最多 2048 字节；有输入积压时跳过。
   128kbps 以下采样间隔至少五秒，512kbps 以下至少两秒，其余至少一秒；浏览器与服务端均限制频率。
   这些限制不含 SCTP/DTLS/IP 开销，不能把遥测负载上限当作全部诊断流量。

## 如何区分原因

新增指标的接口语义遵循 libwebrtc 的 `VideoEncoder::RateControlParameters`，
见 [官方接口](https://webrtc.googlesource.com/src/+/refs/heads/main/api/video_codecs/video_encoder.h)。
实际编译应以编译服务器固定 revision 的头文件为准。

| 连续观察结果 | 下一步检查 |
|---|---|
| 链路估计、视频目标预算和分配码率一起长期低位 | 检查当前选中的 UDP/TURN 路径、持续丢包、限速、拥塞和其他媒体消耗；不能直接提高最低发送码率 |
| 视频目标预算较高，分配码率明显较低 | 检查编码器超调修正、关键帧请求频率和 passthrough 的帧大小/节奏；需要发送端日志或 WebRTC 调试统计进一步确认 |
| 分配码率恢复，配置码率仍低 | 检查实际部署版本、共享编码器的控制者/最弱观看者策略，以及档位稳定窗口；允许观察逐级恢复 |
| JNI 输入明显高于 WebRTC 输出 | 检查编码后进入 VideoStreamEncoder 的丢帧/暂停，不要把所有丢帧归因于网络 |
| WebRTC 输出高，但浏览器解码/呈现低 | 检查 RTP 丢包、重传、关键帧、接收缓冲和浏览器渲染 |
| 静止画面时帧率低，持续滚动时正常 | 属于内容驱动的屏幕采集，需要以持续运动场景验证最大帧率 |

`链路估计` 来自发送端当前选中的 candidate-pair，可能包含其他发送媒体，并非测速结果。
`视频带宽分配` 来自 SetRates，可能大于视频编码目标；`反馈龄` 高也不等于反馈中断，因为 SetRates 按变化触发。
旧 native 库不提供新增字段时，H5 显示缺失值，不用零或其他统计冒充。

## 部署与复测

本次包含 native、Java 策略和 H5 改动；Java JNI 方法签名未改变，但必须部署匹配的新产物才能得到完整诊断。
继续使用独立编译服务器流程，见 [native-build.md](native-build.md)：编译服务器构建并导出配套 `.so`/清单，
APK 服务导入后打包，不在 APK 服务编译 JNI。

1. 更新编译服务器和 APK 服务至同一版本，构建、导入 native bundle，并同步发布 H5。
2. 单观看者、前台标签页，持续滚动或播放运动画面 30–60 秒。分别记录初始、降档后和恢复后的指标。
3. 保留配置上限、`max_fps`、`max_size`、观看者数量、是否 TURN，以及新增的四项反馈指标。
4. 可在受控复测中关闭音频作对照，以区分低带宽下的媒体竞争；不要同时改变其他参数。
5. 若视频目标和链路估计仍长期低位，收集实际选中路径与持续丢包证据后继续定位。
   本次本地回归不证明该云机的 35kbps 根因已经消除，也不替代真实 JNI/APK 构建、弱网与端到端时延测试。

不通过设置 `has_trusted_rate_controller=true` 或关闭拥塞保护来掩盖低帧率。
当前预编码 H.264 经过 VideoStreamEncoder 的依赖帧丢弃风险仍是已知架构限制，见 [commercial-readiness.md](commercial-readiness.md)。
